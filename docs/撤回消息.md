# 机器人如何撤回自己发送的消息

> 本文基于 Gensokyo-ForSpark 实际代码（`handlers/delete_msg.go`、`handlers/message_parser.go`、`msgmap/msgmap.go`）整理，不是照抄 onebot 文档。
> 官方 QQ 机器人协议本身支持「机器人撤回自己发的消息」，Gensokyo 把它包装成 onebot v11 的 `delete_msg`。

## 一、总览：撤回永远是两步

```
① 发送消息 → 回执里拿到 message_id → 自己存起来
② 调 delete_msg,带上那个 message_id(+会话 id)
```

官方接口没有「按群/按时间查历史消息」的能力,所以 **message_id 只能从发送回执里拿**。发送时不存,后面就再也撤不回来了。

---

## 二、第 1 步:拿到 message_id

发送接口成功回执的 `data.message_id` 就是要撤回的 id:

```json
{
  "status": "ok",
  "retcode": 0,
  "data": { "message_id": 1387423 },
  "group_id": 187781763,
  "echo": "..."
}
```

要点:

- **这个 id 是 Gensokyo 压缩后的 idmap 数字,不是官方原始 id**(官方群消息 id 形如 `ROBOT1.0_xxxxxxxx`)。直接把它原样回传给 `delete_msg` 就对了,Gensokyo 会自己反查真实 id。
- 例外:`string_ob11: true` 时不做任何转换,`message_id` / `group_id` 全是官方原始值,应用端自己保管原值。
- 官方消息审核是异步的,即使回执 `retcode: 0` 也可能还在审核;这种情况下立刻撤回有可能成功也有可能报「消息不存在」,属正常。

---

## 三、第 2 步:调用 delete_msg

### 方式 A:WS(onebot 标准 action)

```json
{
  "action": "delete_msg",
  "params": {
    "message_id": 1387423,
    "group_id": 187781763
  },
  "echo": "recall-1"
}
```

### 方式 B:HTTP API

```http
POST http://127.0.0.1:8080/delete_msg
Content-Type: application/json

{"message_id": 1387423, "group_id": 187781763}
```

也支持 GET 查询参数: `GET /delete_msg?message_id=1387423&group_id=187781763`

### 参数

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `message_id` | number / string | ✅ | 发送回执里的 `data.message_id` |
| `group_id` | number / string | 可选(推荐) | 群号(或应用端看到的虚拟群 id);不传则查 msgmap 反查 |
| `user_id` | number / string | 可选(推荐) | 对方 QQ 号 / openid;不传则查 msgmap 反查 |
| `channel_id` | number / string | 可选(推荐) | 子频道 id;不传则查 msgmap 反查 |
| `guild_id` | number / string | 可选(推荐) | 频道私信会话 id;不传则查 msgmap 反查 |

`message_id` 传数字或字符串都行,Gensokyo 在反序列化时会统一转成字符串(`callapi/callapi.go` 的 `ParamsContent.UnmarshalJSON`),不会因为类型不符 panic;`message_id` 完全缺失也不会 panic(2026-09-02 起),只会记一条日志并返回标准响应。

### 成功响应

```json
{ "status": "ok", "retcode": 0, "data": null, "message": "" }
```

标准 onebot v11 形状(`data: null`)。**注意:官方接口调用失败时,Gensokyo 只在日志里打印错误,响应依然是 `ok`** —— 想知道到底撤没撤,看日志里的 `Error retracting group message:`。

## 四、四种会话对应关系

`handlers/delete_msg.go` 里是四条独立分支,按你传的会话字段走不同官方接口:

| 场景 | 传的字段 | 实际调用的官方接口 |
|---|---|---|
| QQ 群 | `group_id` | `DELETE /v2/groups/{group_openid}/messages/{message_id}` → `RetractGroupMessage` |
| QQ 好友(C2C) | `user_id` | `DELETE /v2/users/{openid}/messages/{message_id}` → `RetractC2CMessage` |
| 频道子频道 | `channel_id` | `DELETE /channels/{channel_id}/messages/{message_id}` → `RetractMessage` |
| 频道私信 | `guild_id` | `DELETE /dms/{guild_id}/messages/{message_id}` → `RetractDMMessage` |

**四种都可以只传 `message_id`**:缺会话字段时按 `message_id` 查 `msgmap` 反查目标(2026-09-02 起覆盖出站消息,即机器人自己发的也能反查)。

判定顺序注意:`channel_id` 和 `guild_id` 分支在前面,**同时传了多个会都执行**;正常只传一个。

## 五、六个必踩的坑

### 1. 撤回自己发的消息,带上 `group_id` 最稳

2026-08-20 的修复让 `delete_msg` 支持只传 `message_id`(缺参时从 `msgmap` 反查会话对象),但当时 `msgmap` **只记录机器人收到的入站消息**,机器人自己发出去的消息根本不在表里,所以撤自己的消息只传 `message_id` 是查不到的。

**2026-09-02 已修复**:发送成功后会把 `message_id → 会话对象` 也写入 `msgmap`(标记 `Outbound`),`delete_msg` 的反查也扩展到群 / 私聊 / 频道 / 频道私信四种。现在两种写法都行:

- ✅ 只传 id:`{"message_id": R}` —— 反查群/私聊/频道目标(日志会打印「从msgmap反查到…」)
- ✅ 带上会话 id:`{"message_id": R, "group_id": G}` —— 直连,不查表,最快最稳
- ⚠️ 出站记录同样受 `msgmap` 的 **7 天 TTL** 约束:超过 7 天的消息 id 已被清理,只能靠显式传 `group_id` 撤回
- ⚠️ 应用端**必须在发送回执里拿到并保存** `message_id`,Gensokyo 没有「按群查历史消息」的接口

> 💡 SparkBridge3 的 `spark.QClient.deleteMsg(id)` 只传 `message_id`,在 2026-09-02 的修复前是静默失效的,现在可以直接用。

### 2. 撤回依赖 idmap 数据库,删库就撤不了

`message_id` → 官方真实 id 的映射存在 `idmap.db`(bbolt)里。

- 删掉 / 换机器 / 用另一份 `idmap.db` 启动 → 旧 `message_id` 反查失败 → 官方接口收到空 id → 撤回失败
- `memory_msgid: true` 时映射只在内存,进程重启即丢失(大数据量才开)
- `string_ob11: true` 时根本不走映射,不怕这个

### 3. 权限:自己的能撤,别人的看身份

- 撤回机器人自己发的消息:官方允许,无需额外权限(实际仍受官方风控/审核状态影响)
- 撤回群成员消息:需要机器人在该群有管理员权限(群主授予),否则官方返回无权限,日志里能看到错误
- 私聊里对方的消息:官方无此能力,别指望

### 4. 没有「撤回时限」参数,但超时会被官方拒

官方接口没公开明确的时间窗,实践上越早越稳。机器人被禁言、消息还在审核、消息已被删,都会失败且只体现在日志里。

### 5. 重复撤回不会报错给应用端

已撤回的消息再撤一次,官方返回「消息不存在」,Gensokyo 吞掉后仍回 `ok`。**别用响应判断成败,要用日志**(`mylog` 打印的 `delete_msg: %+v` 与 `Error retracting ...`)。

### 6. hidetip 被固定为 true

四条分支全部带 `openapi.RetractMessageOptionHidetip`,即撤回**不显示**「管理员撤回了一条消息」的系统提示。想保留提示需要改代码,配置里没有开关。

## 六、不想写代码:配置自动撤回

Gensokyo 内置「触发词命中即延时撤回机器人回复」的机制,适合发临时提示(报错、调试信息、限时公告)。

### config.yml

```yaml
settings:
  twoway_echo: true        # 必需:应用端要回填 echo,否则拿不到触发词
  auto_withdraw:           # 触发词前缀列表,命中任一即自动撤回
    - "报错"
    - "调试"
  auto_withdraw_time: 30   # 延迟秒数
```

### 原理(`handlers/message_parser.go`)

1. 应用端发消息时把「触发这条回复的原消息」回填到 `echo`(需 `twoway_echo: true`)
2. Gensokyo 入站时记录 `echo → 触发词原文` 映射
3. 发送成功后,取出该 `echo` 对应的触发词,若以 `auto_withdraw` 里某个前缀开头,则 `sleep(auto_withdraw_time)` 秒后自动构造 `delete_msg` 撤回这条回复

所以**它撤的是机器人自己的回复,判断依据是触发词**,不是消息内容。

## 七、应用端示例

以 SparkBridge3(官方 bot 对接)为例:

```js
// 发送 → 拿 id → 5 秒后撤回自己发的这条
const resp = await spark.QClient.sendGroupMsg(groupId, [
  { type: 'text', data: { text: '这条 5 秒后自动撤回' } }
])
const msgId = resp?.data?.message_id
if (!msgId) return

setTimeout(() => {
  // 标准写法:只传 message_id(Gensokyo 内部反查会话对象)
  spark.QClient.deleteMsg(msgId)
}, 5000)
```

想更稳(不走反查、不受 msgmap TTL 影响),自己拼包带上会话 id:

```js
spark.QClient.sendWSPack({
  action: 'delete_msg',
  params: { message_id: msgId, group_id: groupId }
})
```

HTTP 直连则更直接:

```js
await fetch('http://127.0.0.1:8080/delete_msg', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ message_id: msgId, group_id: groupId })
})
```

> 应用端拿到的 `message_id` / `group_id` 可能是虚拟值,原样回传即可;Gensokyo 自己负责还原成官方值。

## 八、收不到「别人撤回了消息」的通知

官方 QQ 机器人协议目前**不推送撤回事件**。readme 支持列表里写的「群消息撤回 / 好友消息撤回」是上游规划项,本 fork 代码中没有对应实现(全局搜 `recall` 无命中)。

因此:

- 想实现「防撤回」记录 → 做不到,官方不给数据
- 想实现「自己撤回后做后续动作」 → 在你的应用端 `delete_msg` 调用处自己记状态

## 附:调试检查清单

撤不回来时按顺序看:

1. 发送回执里有 `data.message_id` 吗?(没有 → 发送就失败了,`retcode: 0` 也可能是审核失败)
2. 调 `delete_msg` 时带会话 id 了吗?(带了一路直连;没带就看第 3 步的反查日志)
3. 日志有 `delete_msg: 缺省group_id, 从msgmap反查到群[...]` 吗?(没有说明反查没命中 —— 检查是否超过 7 天 TTL、`msgmap.db` 是否是原来那份)
4. 日志有 `Error retracting group message: ...` 吗?(有 → 官方接口拒绝了,看错误内容:权限/消息不存在/审核中)
5. `idmap.db` 是原来那份吗?`memory_msgid` 是否开着重启过?
6. 是否 `string_ob11: true`?(是的话 id 都是原始值,别混用虚拟值)
